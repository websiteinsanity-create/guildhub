# RC3 design recorded before implementation

1. Replace presence-based locks with Linux flock on a stable owner-only writer.lock inode. The application retains the locked open file description; an inherited descriptor lets util-linux flock acquire it synchronously without a Node native dependency. Kernel release follows process death. Never unlink/age-steal an active lock. Ship util-linux and NODE_ENV=production, require explicit mounted directory.
2. Existing established ledgers require the separate DATA_DIR binding. Missing binding fails closed, including an old ledger restored with the binding deleted. Recovery requires an explicitly supplied independently trusted checkpoint; no automatic old-head adoption. Full co-rollback of every local trust anchor remains outside the threat model.
3. Record policy patches rather than full policy snapshots for routine changes. Maintain monotonic logical event sequence and SHA/HMAC chain, supporting RC2 events unchanged.
4. Compact under the same exclusive lock: verify active chain, fsync compressed immutable archive, fsync authenticated state snapshot and fresh journal, then atomically/fsync publish a signed layout pointer. Retain the old generation until that commit. Signed snapshots bind archive digests/ranges and current state. Startup verifies required archives and snapshot; all logical security history remains available. Bounded active replay/storage, finite total-disk budget with warnings; no claim of constant total storage for infinite immutable history.
5. Staged compaction failures never weaken the last published state. Interrupted preparation is discarded only after validating the published generation. Complete authenticated uncheckpointed events replay conservatively. Truncated uncommitted tails require verified committed checkpoints; never silently drop acknowledged events.
6. Import preparation preserves the current policy (apart from conservative invitation invalidation), recording a candidate policy and database digest. Commit after DB replacement; on restart resolve durable intent against the actual database digest. Failed restore must not quarantine previously valid current members.
7. First initialization uses a durable explicit intent containing the exact genesis state/key before publishing components. Interrupted RC3 initialization resumes that intent without inventing history. A signed enrollment marker in DATA_DIR prevents a restored old genesis intent from masquerading as an incomplete first boot after establishment. Key-only interrupted RC2 initialization requires explicit operator acknowledgement and absence of every completed component; never reset an established ledger automatically.
8. Trust: HMAC protects against corruption/unauthenticated mutation, not host root with the key. Local filesystem must provide flock, atomic rename and fsync. Multi-container correctness relies on the SAME underlying inode; separate copies do not share a lock. Docker, real power loss and remote filesystem behavior require staging/host validation.
